## 1. 产品定位与用户画像

### 产品是什么

Pi-Chat 是一个将 [Pi 编程智能体](https://github.com/badlogic/pi) 的终端能力封装为 **多端可视化聊天界面** 的工程。它不是一个独立的 AI 模型，而是一个"壳"——让用户通过熟悉的 ChatGPT 风格界面，远程操控部署在 VPS 上的 Pi Agent，进行代码编写、文件操作、项目管理等编程任务。

### 核心价值主张

> "在手机上写代码，和在终端前一样高效。"

具体而言：
- **远程编程**：Pi Agent 跑在 VPS 上，用户在任何设备上发起指令，Agent 在服务器本地执行（读写文件、运行命令），不受本地设备性能限制。
- **后台持久化**：关闭 App/浏览器不打断正在执行的长任务，重新打开自动追回进度。
- **多端协同**：Web、Android、鸿蒙三端共享同一份会话历史和同一个 Agent 进程池。

### 用户画像

| 画像 | 描述 | 典型场景 |
|:---|:---|:---|
| **远程开发者** | 有 VPS/云服务器，熟悉命令行，希望在移动端也能操控服务器上的编程任务 | 通勤路上用手机查看 Agent 的代码修改进度，回到电脑无缝继续 |
| **多设备工作者** | 在不同设备间切换工作（公司电脑、个人手机、平板） | 在公司 Web 端发起一个重构任务，路上用 Android 查看进度并插话调整方向 |
| **Pi Agent 重度用户** | 已在使用 `pi` CLI，希望有更好的可视化界面 | 用 Web 界面替代终端，享受 Markdown 渲染、思考过程折叠、工具调用可视化 |

## 2. 系统拓扑与用户触点

```
用户手持设备
├── 🌐 Web 浏览器 ──────────────┐
├── 📱 Android App ─────────────┤
└── 📱 HarmonyOS App ───────────┤
                                 │
                    WebSocket / REST (JSON + Token)
                                 │
                                 ▼
                    ┌─────────────────────────┐
                    │   VPS 网关服务 (server)  │
                    │   • Token 鉴权            │
                    │   • 进程池管理            │
                    │   • 离线事件缓存          │
                    │   • 30s 心跳保活          │
                    └────────────┬────────────┘
                                 │ stdin/stdout (JSON RPC)
                                 ▼
                    ┌─────────────────────────┐
                    │   pi --mode rpc 子进程    │
                    │   • LLM 推理              │
                    │   • 本地工具执行           │
                    │   • 会话持久化 (.jsonl)    │
                    └─────────────────────────┘
```

**用户可见的触点**：
1. **客户端 App/页面** —— 唯一直接交互的界面
2. **服务器地址 + Token** —— 连接配置（一次性）
3. **工作目录 (CWD)** —— 告诉 Agent 在哪个项目目录下工作
4. **会话列表** —— 历史对话记录
5. **聊天界面** —— 发送指令、查看回复

**用户不可见（但影响体验）的环节**：
- 网关进程池调度（多会话共享/隔离）
- 离线事件环形缓存与回放
- Agent 子进程的空闲回收
- WebSocket 代次标记防竞态

## 阶段二：首次配置与连接

### 2.1 Web 端配置流

```
用户打开 http://localhost:3000
  │
  ├─ 场景 A: 本地无鉴权 (AUTH_TOKEN 为空)
  │   → 页面直接显示聊天界面，已连接 ✓
  │   → 左下角显示 "已连接" 绿色指示灯
  │   → 侧边栏显示空会话列表
  │
  ├─ 场景 B: VPS 有鉴权
  │   → WebSocket 连接被拒绝 (401)
  │   → 浏览器弹出 prompt: "Pi Gateway 开启了访问鉴权，请输入访问 Token："
  │   → 用户输入 Token → 存入 localStorage → 自动重连 ✓
  │
  └─ 场景 C: 首次使用，不知道服务器在哪
      → 页面显示 "已断开" 红色指示灯
      → 用户需要先在 VPS 上启动网关服务
      → 然后在浏览器地址栏访问 VPS 地址
```

### 2.2 Android 端配置流

```
用户打开 App
  │
  ├─ 首次启动
  │   → 默认服务器地址: http://10.0.2.2:3000 (模拟器映射宿主机)
  │   → 点击右上角 ⚙️ 设置按钮
  │   → 填入 VPS 网关地址 (如 http://192.168.1.100:3000)
  │   → 填入访问 Token (如有)
  │   → 点击 "保存并重连"
  │   → 连接状态指示灯变绿 ✓
  │
  └─ 后续启动
      → 自动读取上次保存的地址和 Token
      → 自动连接 ✓
```

### 2.3 HarmonyOS 端配置流

```
用户打开 App
  │
  ├─ 首次启动
  │   → 从 PreferencesHelper 读取服务器地址
  │   → 无保存记录时回退到 http://10.0.2.2:3000
  │   → 点击 ⚙️ 设置按钮 → 弹出服务器配置对话框
  │   → 输入地址 → "保存并重连"
  │   → 地址持久化到 PreferencesHelper ✓
  │
  └─ 后续启动
      → 自动从 PreferencesHelper 读取并连接 ✓
```

### 2.4 选择工作目录 (CWD)

连接成功后，用户需要告诉 Agent 在哪个目录下工作：

| 端 | 操作方式 | 验证机制 |
|:---|:---|:---|
| Web | 侧边栏顶部 CWD Pill → 点击弹出路径输入对话框 + 快捷芯片 | 服务端 `/api/validate-dir` 验证 |
| Android | 设置界面中配置 CWD + 快捷芯片 | 保存后自动重连 WebSocket |
| HarmonyOS | 设置中可配置工作目录 | 协议支持 |

## 阶段三：核心对话体验

这是用户旅途中最核心、最高频的部分。

### 3.1 发送第一条消息

```
用户在输入框输入: "帮我看看这个项目的目录结构"
  │
  ├─ 客户端发送 WebSocket 消息:
  │   { type: "prompt", message: "帮我看看这个项目的目录结构", id: "xxx" }
  │
  ├─ 服务端收到后:
  │   → 广播 { type: "remote_user_prompt", message: "..." } 给同会话其他连接
  │   → 转发给 pi 子进程: { type: "prompt", message: "...", id: "xxx" }
  │
  ├─ pi Agent 开始处理:
  │   → 服务端收到 { type: "agent_start" } → 广播给客户端
  │   → 客户端 UI: 发送按钮变为 "⏹ 停止" 状态
  │
  ├─ Agent 思考中:
  │   → { type: "message_update", assistantMessageEvent: { type: "thinking_delta", delta: "..." } }
  │   → 客户端 UI: 显示 "Thinking Process" 折叠卡片，实时累加思考内容
  │   → 卡片标题显示实时计时: "Thinking in progress… 3.2s"
  │
  ├─ Agent 调用工具:
  │   → { type: "message_update", assistantMessageEvent: { type: "toolcall_start", toolCall: { name: "bash", ... } } }
  │   → 客户端 UI: 显示工具调用卡片 "💻 bash"，可折叠展开
  │   → 工具执行中: 动态更新输入参数、标准输出
  │   → 工具完成: 显示执行状态和耗时
  │
  ├─ Agent 输出文本:
  │   → { type: "message_update", assistantMessageEvent: { type: "text_delta", delta: "..." } }
  │   → 客户端 UI: 流式打字机效果，实时渲染 Markdown
  │
  └─ Agent 完成:
      → { type: "agent_settled" }
      → 客户端 UI: 恢复发送按钮，标记流式结束
      → 侧边栏会话列表刷新（更新最后消息预览和时间）
```

### 3.2 流式渲染体验细节

用户在屏幕上看到的是**逐字浮现**的回复，而非一次性出现。具体表现：

| 事件类型 | UI 表现 | 用户感受 |
|:---|:---|:---|
| `thinking_delta` | 紫色折叠卡片，标题 "Thinking Process"，内容实时累加 | "能看到 AI 的思考过程，很透明" |
| `toolcall_start` | 工具卡片出现，显示工具名（💻 bash / 📄 read / ✏️ edit） | "知道 AI 在做什么操作" |
| `tool_execution_update` | 工具卡片内实时显示输出 | "能看到命令执行结果" |
| `text_delta` | 消息正文区域逐字出现，Markdown 实时渲染 | "像 ChatGPT 一样的打字机效果" |
| `agent_settled` | 思考卡片标题变为 "用时 3.2s"，工具卡片显示总耗时 | "知道这次回复花了多久" |

### 3.3 中途插话 (Steering) —— 差异化亮点

当 Agent 正在执行长任务时，用户不需要等待完成，可以直接输入补充指令：

```
场景: Agent 正在执行 "重构整个认证模块"（预计需要 2 分钟）

用户输入: "等等，先别动 auth.js，那个文件我刚改过"
  │
  ├─ 客户端发送: { type: "steer", message: "等等，先别动 auth.js..." }
  ├─ 服务端转发给 pi 子进程
  ├─ Agent 收到后调整后续行为
  └─ 用户看到: Agent 的后续输出中考虑了这条插话指令
```

**用户感受**：*"这个功能太实用了！以前用 CLI 的时候只能等它跑完再说，现在可以随时纠偏。"*

### 3.4 中止生成 (Abort)

```
用户点击 "⏹ 停止" 按钮
  │
  ├─ 客户端发送: { type: "abort" }
  ├─ 服务端转发给 pi 子进程
  ├─ Agent 中断当前生成
  └─ 客户端 UI: 恢复发送按钮，保留已生成的部分内容
```

## 阶段四：会话管理与多端协同

### 4.1 会话列表

```
用户打开侧边栏 (Web: 左侧面板 / Android: 抽屉导航 / HarmonyOS: SideBarContainer)
  │
  ├─ 客户端调用 REST API: GET /api/sessions?cwd=/path/to/project
  │
  ├─ 服务端扫描 sessionsDir 下的 .jsonl 文件
  │   → 解析每个文件的 session header、首条用户消息、消息计数
  │   → 按时间戳降序排列
  │   → 返回 { cwd, sessions: [...] }
  │
  └─ 客户端渲染会话列表:
      → 每条显示: 会话名/首条消息预览 + 时间
      → 点击切换到该会话
```

### 4.2 新建会话

```
用户点击 "+ New" / "+" 按钮
  │
  ├─ 客户端发送 WebSocket: { type: "new_session" }
  │
  ├─ 服务端处理:
  │   → 如果当前 Agent 有会话或正在忙: 分离当前 WS → 创建新 Agent → 附加 WS
  │   → 否则: 清空事件缓冲 → 直接在当前 Agent 上创建新会话
  │
  ├─ pi 子进程创建新的 .jsonl 会话文件
  │
  └─ 客户端 UI:
      → 清空聊天区域
      → 标题变为 "新对话"
      → URL 更新 (Web 端移除 ?session= 参数)
```

### 4.3 切换会话

```
用户点击会话列表中的某条历史会话
  │
  ├─ 客户端先加载历史消息: GET /api/session?file=xxx.jsonl
  │   → 服务端读取 .jsonl 文件，解析为消息链
  │   → 返回 { header, entries, model, sessionName }
  │   → 客户端渲染历史消息
  │
  ├─ 然后建立 WebSocket 连接: WS /ws?cwd=...&session=xxx.jsonl
  │
  ├─ 服务端查找/创建对应的 Agent 进程
  │   → 如果该会话已有 Agent 在运行: 附加 WS，共享进程
  │   → 如果没有: 创建新 Agent，启动 pi 子进程
  │
  └─ 离线事件回放 (Backfill):
      → 如果该 Agent 有离线期间缓存的事件:
         1. 客户端收到 { type: "backfill_start", count: N }
         2. 客户端收到 N 条离线事件 (text_delta, toolcall 等)
         3. 客户端收到 { type: "backfill_end", streaming: false, state: "idle" }
      → 客户端在回放期间暂停自动滚动，回放结束后一次性同步状态并滚动到底部
```

### 4.4 删除会话

```
用户在会话列表中触发删除操作
  │
  ├─ 客户端调用 REST API: DELETE /api/session?file=xxx.jsonl
  │
  ├─ 服务端处理:
  │   → 路径安全校验 (防止路径遍历攻击)
  │   → 停止对应的 Agent 进程 (如果有)
  │   → 删除 .jsonl 文件
  │
  └─ 客户端从会话列表中移除该项
```

### 4.5 重命名会话

```
用户在会话上触发重命名
  │
  ├─ 客户端发送 WebSocket: { type: "set_session_name", name: "新名称" }
  ├─ 服务端转发给 pi 子进程
  ├─ pi 在 .jsonl 文件中写入 session_info 记录
  └─ 会话列表刷新，显示新名称
```

### 4.6 多端协同场景

```
场景: 用户在公司电脑 Web 端工作，需要出门

1. 公司电脑 Web 端:
   → 用户发起 "重构认证模块" 任务
   → Agent 开始执行（预计 5 分钟）
   → 用户关闭浏览器标签页

2. 服务端:
   → WebSocket 断开，但 Agent 进程不终止
   → Agent 继续执行，输出事件存入环形缓冲区 (最多 5000 条)

3. 用户在路上打开 Android App:
   → 连接到同一个 VPS 网关
   → 选择同一个会话
   → 服务端发现该会话的 Agent 还在运行
   → 附加新的 WebSocket 连接到同一个 Agent
   → 触发 Backfill: 将离线期间缓存的事件回放给 Android 客户端
   → Android 端显示: Agent 已经完成了 60% 的重构工作

4. 用户在 Android 上插话:
   → 发送 steer 消息: "跳过 test/ 目录的修改"
   → Agent 调整后续行为
   → 回到电脑后，Web 端重新打开同一会话，看到完整结果
```

**用户感受**：*"关了浏览器任务还在跑，手机上打开直接看到进度，这才是真正的远程编程。"*

### 4.7 后台持久化的技术保障

| 机制 | 说明 | 用户感知 |
|:---|:---|:---|
| **进程池化** | 以 `${cwd}:${sessionPath}` 为 Key，多端连接共享同一个 Agent 进程 | 多设备看到的是同一个任务进度 |
| **离线环形缓冲** | 无连接时事件存入 5000 条容量的环形队列 | 重连后不丢失任何输出 |
| **真·空闲回收** | 仅在无连接 + 进程完全 idle 时启动 5 分钟回收倒计时 | 关闭页面后任务不会被打断 |
| **30s 心跳保活** | 服务端每 30s 发送 WebSocket ping | 连接不会因网络中间件超时断开 |

## 阶段六：异常场景与恢复

### 6.1 网络断开与自动重连

```
场景: 用户正在对话，手机突然失去网络连接
  │
  ├─ WebSocket onclose 触发
  │
  ├─ Web 端:
  │   → 连接状态指示灯变红 "已断开"
  │   → 启动定时器尝试重连 (scheduleReconnect)
  │   → 网络恢复后自动重连
  │   → 重连成功后显示 Toast "网络连接已恢复"
  │   → 自动同步当前会话历史 + 触发 Backfill
  │
  ├─ Android 端:
  │   → 连接状态变为 DISCONNECTED
  │   → 指数退避重连
  │   → 重连后恢复会话
  │
  └─ HarmonyOS 端:
      → 自动重连机制
      → 重连后恢复状态
```

### 6.2 Agent 进程异常退出

```
场景: pi 子进程崩溃或被 kill
  │
  ├─ 服务端检测到子进程退出
  ├─ 广播: { type: "pi_exit", ... } 给所有连接的客户端
  ├─ 客户端显示错误提示
  └─ 用户重新发送消息时，服务端自动创建新的 Agent 进程
```

### 6.3 鉴权失败

```
场景: Token 过期或错误
  │
  ├─ Web 端: WebSocket 收到 { type: "error", code: "unauthorized" }
  │   → 弹出 prompt 重新输入 Token
  │   → 输入后自动重连
  │
  ├─ Android/HarmonyOS: 设置界面重新输入 Token
  │
  └─ 鉴权超时: WebSocket 连接后 3 秒内未发送 auth 消息 → 关闭连接 (4401)
```

### 6.4 并发连接与竞态处理

```
场景: 用户快速切换会话，旧连接的消息还在路上
  │
  ├─ 服务端为每个 WebSocket 分配递增的代次号 (wsGen)
  ├─ 客户端在收到消息时检查 ws._gen === wsGen
  ├─ 旧连接的消息被丢弃，不污染新会话状态
  │
  └─ 用户无感知，不会看到"串会话"的异常
```

### 6.5 容量限制

```
场景: 服务端配置了 MAX_CONCURRENT_AGENTS 限制
  │
  ├─ 新连接时如果超过限制:
  │   → WebSocket 收到 { type: "error", code: "capacity", message: "..." }
  │   → 连接被关闭 (1013)
  │
  └─ 用户需要等待其他会话的 Agent 空闲回收后才能连接
```

## 11. 用户痛点与改进建议

### 11.1 已识别的痛点

| # | 痛点 | 严重度 | 影响阶段 | 端 |

### 11.2 改进建议

#### 高优先级

1. **Web 端 Token 输入改为模态对话框**：替换原生 `prompt()`，提供更美观的输入界面，支持"记住 Token"选项。

2. **移动端扫码配置**：在 Web 端生成配置二维码（含服务器地址 + Token），移动端扫码一键导入，消除手动输入的繁琐和出错。

3. **HarmonyOS 功能补齐**：完成图片上传 UI 和 Markdown 导出功能，实现三端完全对齐。

#### 中优先级

4. **会话搜索**：在会话列表中增加搜索框，支持按会话名/首条消息模糊匹配。

5. **CWD 概念简化**：对非技术用户提供"项目"概念替代"工作目录"，展示最近使用的项目列表而非裸路径。

6. **HarmonyOS 版本号动态化**：将侧边栏硬编码的 `v2.11.3` 改为从 `app.json5` 动态读取，跟随 lockstep 版本。

#### 低优先级

7. **消息内搜索**：支持在当前会话内搜索关键词，高亮匹配位置。

8. **离线缓存**：客户端本地缓存最近会话内容，服务端不可达时可查看历史（只读模式）。

## 总结

Pi-Chat 的用户旅途核心是一条 **"配置 → 对话 → 管理 → 协同"** 的闭环：

1. **配置门槛适中**：需要 VPS + Pi Agent 的前置条件，但对目标用户（远程开发者）来说不算障碍。`npx` 一键启动是最低门槛入口。

2. **核心对话体验优秀**：流式打字机、思考过程可视化、工具调用卡片、中途插话——这些功能组合在同类产品中具有差异化竞争力。

3. **多端协同是最大亮点**：后台持久化 + 离线回放 + 进程共享，真正实现了"关了电脑用手机继续"的远程编程体验。

4. **异常处理较为完善**：自动重连、心跳保活、代次防竞态、路径安全校验等机制覆盖了常见的异常场景。

5. **改进空间集中在**：首次配置的便捷性（扫码）、HarmonyOS 功能补齐、会话/消息搜索等效率功能。
